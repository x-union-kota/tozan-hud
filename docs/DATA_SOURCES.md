# DATA_SOURCES.md — データソース改定仕様(v3.2計画)

現状のデータ取得を「一番良い公開データ」に置き換えるための仕様。優先度順。
すべて オフライン2段構え(ユーザーが手元でDL → tools/ が焼き込み)か、
既存のsw.jsキャッシュが効くランタイム取得のどちらかに収める。
コンテナ/サンドボックスから外部APIへの直接アクセスは不可の前提を維持すること。

---

## 優先1: 地形 — 陰影起伏図(ラスタ) → 標高タイル(数値DEM) へ切替

### 現状の問題
`app.js` の地形レイヤは `hillshademap`(誰かが描いた影絵のラスタ)を **z13固定** で取得し反転している。
- 解像度が低い(z13 ≈ 19m/px、しかも影絵の再サンプル)
- 描画を自前制御できない(反転しかできず、加算ディスプレイ向けの明度設計が不可能)
- 平坦地(urban)では中身がほぼ無地

### 切替先: 地理院 標高タイル(PNG形式)
- 10mメッシュ: `https://cyberjapandata.gsi.go.jp/xyz/dem_png/{z}/{x}/{y}.png` (〜z14)
- 5mメッシュ(航空レーザ): `https://cyberjapandata.gsi.go.jp/xyz/dem5a_png/{z}/{x}/{y}.png` (z15。山岳部は欠損域あり→dem_pngへフォールバック)
- テキスト形式(`.../dem/{z}/{x}/{y}.txt` 等)もあるが、ランタイムはPNGが軽い
- **ホストが現行と同じ cyberjapandata.gsi.go.jp なので sw.js のタイルキャッシュはそのまま効く**
- 出典明示は現行と同じ「地図: 地理院タイル」でよい

### PNG→標高のデコード(実装必須の式)
ピクセル(R,G,B)に対し `x = R*65536 + G*256 + B` として
- `x < 2^23` → 標高 = x * 0.01 (m)
- `x = 2^23` → 無効
- `x > 2^23` → 標高 = (x − 2^24) * 0.01 (負値)
- 無効値は (R,G,B) = (128,0,0)
canvas に描いて getImageData でデコードする(現行の反転処理と同じ経路で書ける)。
※ canvasのアルファ合成で値が壊れないよう `crossOrigin='anonymous'` と不透明描画を維持すること。

### 実装タスク
**1〜3 は v3.2 で実装済み。残りは 4(1mメッシュGML・優先度低)のみ。**

1. ✅ `buildTerrain` を「陰影反転」→「DEMデコード→自前レンダ」に差し替え
   - 描画は加算ディスプレイ前提で設計: 黒地に尾根線・等高線を高輝度で。グレー階調のベタ塗り禁止(ガイドの配色原則)
   - 勾配(隣接ピクセル差分)から陰影を計算し、明部のみ光らせる。または等高線抽出(一定標高間隔の等値線)
2. ✅ ズームをルート実寸に応じた適応型に(上限: dem5a_png=z15 / dem_png=z14。欠損はフォールバック)
   → 実装: タイル12枚に収まる最大ズームを選択。dem5aの取得失敗が半数超なら dem_png(z14) で再取得。
   等高線間隔は起伏レンジだけでなく**画面上の勾配(m/px)**からも決める(急斜面での線の潰れ防止)
3. ✅ 同じDEMデコーダを `tools/` 側にも移植し、以下を解禁:
   - **DEMレイキャストによる可視判定の自動化**(gpx2route.py: ルート上サンプル点→対象方位へ標高プロファイルを引き、遮蔽チェック。`v:1` を自動付与し、`--vis` は上書き手段に格下げ)
   - 標高なしGPX・POIの標高補完の精度向上
   - 断面図データの検証(GPXのele信頼性チェック)
   - ※ツール側はタイルをユーザーが手元でDLして投入する形(`--dem-tiles dir/` 等)。curl一括DLスクリプトの雛形を `--emit-dem-fetch` として出力すると親切
   → 実装: `--emit-dem-fetch` / `--dem-tiles` / `--dem-zoom`(既定12) / `--dem-src` / `--dem-radius-km`。
   PNGデコードは stdlib の zlib のみ(Pillow不要)。可視判定は地形側を `elev_max` で見て遮蔽側へ倒し、
   両端は自分の足元に遮られないよう除外。DEM欠損を含む視線は「不明」で `v:0` のまま。
4. ⬜ 基盤地図情報の **1mメッシュDEM**(提供範囲は国土の約6割、東京23区含む。https://service.gsi.go.jp/kiban/ 無料登録DL、GML形式)は焼き込み用の上位互換として `--dem-gml` 投入口を検討(優先度低)

## 優先2: 街中 — タイルをやめてOSM道路ベクタを焼き込む

### 問題
平坦地はDEMを良くしても無地。ラスタ地図(標準/淡色/OSMタイル)の反転は
細線が灰色のモヤになり加算ディスプレイで死ぬ(ガイド「グレー階調は屋外で消える」)。

### 仕様
gpx2route.py のオフライン2段構えを拡張:
1. `--emit-query` に highway / waterway / railway の way 取得を追加(ルートbbox+マージン、`out geom`)
2. 応答から折れ線を抽出し、道路クラスで間引き(motorway〜tertiary+ルート近傍のそれ以下)、
   Douglas-Peucker簡略化(tol 10m目安)、ルートのpolyと同じ差分圧縮でルートオブジェクトに焼き込み(例: `vec:{road:[...],water:[...],rail:[...]}`)
3. app.js の地図パネル: `route.vec` があれば黒地に線描画(道路クラスで明度差、水域は暗めの面か輪郭線、鉄道は破線)。domainがurbanのときの既定表示にする
4. サイズ予算: 1ルートあたり +10〜30KB 目安。超えるときは間引きを強める(HTML全体の肥大に注意)
5. 出典: OSMはODbL。クレジット表記を「地図: 地理院タイル / © OpenStreetMap contributors」に拡張

### 実装状況(v3.2)
**1〜5 と `--snap-osm` は実装済み(優先2 完了)。**
3(app.js の描画)は「非活性色1色・道路クラスは太さ・鉄道と水域は線種」で実装した。
明度差で区別する案は採らない — 加算ディスプレイでは地図が明るいとルート(#ffd83b)を食う。
クラスごとの採用距離も変えてある(cls≥3は margin全域 / cls2は200m / cls1は80m)。
都市部で歩道・細街路まで全部拾うと線が塊になって地図として読めなくなるため。

### ルートの道路吸着 `--snap-osm`(実証済み・必須)
定義: **「描かれた道路の実ジオメトリ=走るべき道」**。概形ルートや荒れたGPXを、同じOSMデータの道路網へ射影して一致させる。
実証(皇居ラン概形×実OSM): ズレ 平均19.6m / 最大77.4m — **逸脱警告の発火閾値(50m)を超えるズレが概形に内在していた**ので、これは見た目でなく機能の修正。
- ルートを10m間隔に密化 → 各点を最近傍の道路セグメントへ射影
- 候補道路から `motorway*` を除外(首都高等の車専用道へ吸着させない)
- 射影距離が60m超の点は吸着せず原座標を維持(堀・ブロック越えの誤吸着防止)
- 吸着後にDouglas-Peucker再簡略(皇居ラン実測: 164点・約2KB)
- 適用条件: `--osm` 併用時に既定ON、`--no-snap` で無効化。mountainドメインではpath/track/footway系を主候補にする

#### 実装で判明: 「最近傍射影」だけでは足りない(v3.2 実測)
上の仕様どおり点ごとの最近傍射影を実装したところ、**ずれも距離も悪化した**。
密な都市部では点ごとに別の道を選んでしまうため。合成の荒れGPX(σ=6m)を正解の道へ戻す実験で:

| 段 | 距離(正解1199m) | 正解とのずれ |
| --- | --- | --- |
| 荒れGPX | 2171m (+81%) | 平均6.4m |
| 点ごとの最近傍射影のみ | ほぼ改善せず(道を跳び移る) | 悪化 |
| **① Viterbiで系列全体を解く** | | |
| **② 同一道路上の弧長を単調化** | 1413m (+18%) | 平均4.7m |

必要だったのは次の3段。仕様を実装する人は①②を落とさないこと:
1. **系列をViterbiで解く** — 放射コスト=射影距離 / 遷移コスト=|間隔−step|+道が変わるなら罰則。
   点ごとの独立な最近傍選択では、平行する歩道の間を1点ごとに行き来する
2. **同じ道に乗っている区間は弧長を単調化する** — 射影は横ずれしか消さない。
   縦方向のノイズが残るため距離が大幅に水増しされる(これが+80%の正体)。
   ただし単調化で60mを超えて押し出される点は生の射影に戻す(`--snap-max` の約束を破らない)
3. **「吸着しない」を候補に含める** — 道から離れた区間は原座標を維持する

概形ルート(実在の道と1対1に対応しない)は完全には戻せない。皇居ラン概形では 5.0km→5.6km(+12%)。
距離はCT・ペース・残距離の土台なので、**10%以上変わったら警告を出す**実装にしてある。

## 優先3: 星表 — 手動69星 → HYG Database + Stellarium星座線【v3.2 実装済み】

要件「300星+88星座」を公開データで満たす。※当初案はBSC5+d3-celestialだったが、
HIP番号で両者が結合できる以下の組に決定(HYGはBSC5等を統合したCSVでパースも楽)。
- 星: **HYG Database** `hygdata_v3.csv`(CC BY-SA。等級・赤経赤緯・固有名・HIP番号)
- 星座線: **Stellarium** `constellationship.fab`(88星座の線分がHIP番号で定義済み)
- 投入口: `make_stars.py --hyg <csv> --lines <fab>`(オフライン2段構え)

実装上の必須注意:
1. **星座線が参照する星は等級カットの例外にする。** ラベル用は明るい星のみ(3.5等≈300星目安)でよいが、
   fabの線分がHIP参照する星は暗くても座標を収録しないと線が欠ける。「ラベル用」と「線の頂点用」を分けて持つ
2. **ライセンス表記**: HYG=CC BY-SA(要クレジット)、Stellarium星座線=GPL系。READMEと診断画面に
   「星表: HYG Database (CC BY-SA) / 星座線: Stellarium」を追記
3. 既存の和名テーブル(ベガ→こと座 等)は上書き辞書として維持
- サイズ予算: stars.js は 15KB 以内目安(現行3.9KB)

### 実装結果(v3.2)と、仕様からのズレ
ラベル用288星(≤3.5等)+ 線の頂点専用444星 + 88星座695線分。**stars.js は 14.8KB**。

**入手先が仕様と変わっていた(2026-08 実地確認)**:
- Stellarium の `constellationship.fab` は**廃止**され、modern スカイカルチャは `index.json` に移行。
  `constellations[].id = "CON modern Aql"` / `lines` は HIP番号の**折れ線**の配列(線分の対ではない)。
  `make_stars.py` は index.json と旧 .fab の両方を判別して読む。
  `https://raw.githubusercontent.com/Stellarium/stellarium/master/skycultures/modern/index.json`
- HYG は `hyg/CURRENT/hygdata_v40.csv.gz`(13MB)。`.gz` のまま渡せる。
  `https://raw.githubusercontent.com/astronexus/HYG-Database/main/hyg/CURRENT/hygdata_v40.csv.gz`
- 両方とも `make_stars.py --emit-fetch` が出力する

**等級カット例外の実測値**: 695線分のうち **520本(75%)** が3.5等より暗い星を参照している。
ある夜の画面で言うと、描画中49本のうち **39本(80%)** が頂点用を落とすと消える。
「あると良い」ではなく、無いと星座線機能が成立しない。

**サイズ**: JSONの生配列だと23KBで、等級カットを下げても星が `s` から `v` へ移るだけで減らなかった
(mag≤3.0 でも22.3KB)。座標は `CORE.decodePoly`、等級と線の添字は `CORE.decodeEle` で戻せる
差分符号化にして14.8KB。アプリ側に新しいデコーダは足していない。

## 優先4: 磁気偏角 — ハードコード7.5° → 世界磁気モデル(WMM)

- NOAA **WMM係数ファイル**(WMM.COF、数KB、パブリックドメイン): https://www.ncei.noaa.gov/products/world-magnetic-model
  ※モデルは5年更新(現行はWMM2025、有効2025〜2030)。有効期限チェックを入れる
- gpx2route.py に球面調和計算(〜150行)を実装し、ルート重心+現在日付から偏角を自動算出。`--dec` は上書き手段に格下げ
- 検証: 地理院の磁気図の値と主要地点で±0.3°以内に合うことをテスト化

## 現状維持でよいもの

- 天気: Open-Meteo(現行) — 適切
- POI/峰: OSM Overpass(v3.1で実装済み) — 適切。内蔵著名峰DBもそのまま
- CT: 標準式自動生成+`--ct`手動 — 公開の標準CTデータは存在しないため現状が最善

## 共通ルール

- 新しいデータ投入口はすべて「手元DL→ツール投入」のオフライン2段構え(gpx2route.py の `--emit-query`→`--osm` が型)
- 取得手段(クエリ/URL/curl例)はツール自身が出力する(ユーザーがドキュメントを探さなくて済むように)
- ライセンス: 地理院=出典明示 / OSM=ODbL表記 / HYG Database=CC BY-SA(要クレジット・データ部分は継承) /
  Stellarium星座線=GPL系 / WMM=パブリックドメイン。クレジット行の表示を忘れない
- 各投入口に必ず機械テストを付ける(合成データで。gpx2route.test.py が型)
